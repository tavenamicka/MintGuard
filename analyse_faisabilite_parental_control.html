2️⃣ Blocage des Sites Web

Approche 1: DNS Filtering (Recommandée - Plus Simple)

dnsmasq

✓ Léger et rapide

✓ Pas besoin d'intercepter HTTPS

✗ Facile à contourner (VPN, changer DNS)

/etc/hosts

✓ Très simple à implémenter

✗ Facile à modifier si l'utilisateur a accès

✗ Scalabilité (milliers d'entrées)

Implémentation DNS avec dnsmasq :

# Configuration dnsmasq address=/facebook.com/127.0.0.1 address=/tiktok.com/127.0.0.1 address=/youtube.com/127.0.0.1 # Écouter sur localhost:5353 listen-address=127.0.0.1 port=5353 # Rediriger les requêtes DNS système

Approche 2: Proxy HTTP/HTTPS (Plus Sécurisé)

Squid Proxy

✓ Inspection HTTP/HTTPS possible

✓ Filtrage granulaire (par URL, domaine)

✗ Complexe à configurer

✗ Performance (ralentit les connexions)

mitmproxy

✓ Man-in-the-middle HTTPS

✓ Très flexible

✗ Nécessite certificat CA local

✗ Haute complexité

⚠️ Limitation HTTPS: L'interception HTTPS requiert un certificat de CA (Certificate Authority) local sur la machine enfant. L'utilisateur peut le désinstaller s'il a les droits administrateur. Solution : utiliser les permissions et AppArmor pour empêcher sa suppression.

Approche 3: Firewall Level (iptables)

# Bloquer par IP (après DNS lookup) iptables -A FORWARD -d 31.13.64.0/18 -j DROP # Facebook iptables -A FORWARD -d 192.173.64.0/18 -j DROP # YouTube # Avantages: aucun, pour du filtrage web # Désavantages: IP change, CDN rend impossible à maintenir
Méthode Sécurité Performance Complexité Contournement
dnsmasq Faible Excellent Facile VPN, DNS custom, hosts local
Squid Proxy Moyen Bon Complexe VPN, Tor, proxy local
mitmproxy Moyen Moyen Très complexe Suppression certificat CA

3️⃣ Limitation du Temps d'Utilisation

Approche 1: Session Lock (Recommandée)

Approach: systemd + Service

# Service systemd: /etc/systemd/system/parental-timer.service [Unit] Description=Parental Control Timer After=multi-user.target [Service] Type=simple User=root ExecStart=/usr/local/bin/parental-timer.py Restart=always [Install] WantedBy=multi-user.target

Implémentation (pseudo-code Python) :

import subprocess from datetime import datetime, time RESTRICTED_USER = "child" ALLOWED_HOURS = { "monday": ("16:00", "20:00"), "saturday": ("10:00", "22:00"), "sunday": ("10:00", "21:00") } while True: now = datetime.now() day = now.strftime("%A").lower() current_time = now.time() if day in ALLOWED_HOURS: start, end = ALLOWED_HOURS[day] start_t = time.fromisoformat(start) end_t = time.fromisoformat(end) if not (start_t <= current_time <= end_t): # Hors des heures autorisées subprocess.run(["loginctl", "terminate-user", RESTRICTED_USER]) log_action("User locked out - outside allowed hours") time.sleep(60) # Vérifier toutes les minutes

Approche 2: cgroups/systemd (Contrôle fin)

# Limiter CPU/Memory pour l'utilisateur enfant [Service] User=child CPUQuota=30% MemoryLimit=500M

Approche 3: Accès clavier/souris bloqué

Nécessite: root

# Utiliser /dev/input/event* pour bloquer périphériques # Avantage: empêche totalement l'interaction # Désavantage: contrôle grossier chmod 000 /dev/input/event0 # Bloquer clavier
Méthode Efficacité Contournement Complexité Implémentation
Session Logout Très bonne Re-login si password connu Facile
cgroups Bonne Pas vraiment contournable Moyen
Clavier/Souris Excellente Difficile sans accès physique Facile

4️⃣ Blocage des Applications

Approche 1: Permissions Fichiers (Simple mais Imparfait)

# Rendre inévitable un exécutable chmod 000 /usr/bin/firefox chmod 000 /opt/discord/Discord # Problème: L'utilisateur peut changer permissions # Solution: Utiliser AppArmor/SELinux

Approche 2: AppArmor (Recommandée pour Linux Mint)

Niveau: Kernel

# Profil AppArmor: /etc/apparmor.d/restrict-child profile restrict-child flags=(attach_disconnected) { include <abstractions/base> # Bloquer Firefox deny /usr/bin/firefox rx, deny /usr/lib/firefox/** rx, # Bloquer Chrome deny /usr/bin/google-chrome rx, deny /opt/google/** rx, # Bloquer Steam deny ~/.steam/** rwx, deny ~/.local/share/Steam/** rwx, # Autoriser applications essentielles allow /bin/** rx, allow /usr/bin/bash rx, allow /usr/bin/python3 rx, }

Activation :

# Parser le profil apparmor_parser -r /etc/apparmor.d/restrict-child # Charger au démarrage de session enfant # Dans ~/.bashrc ou pam_apparmor sudo -u child aa-exec -p restrict-child -- bash

Approche 3: SELinux (Plus Puissant, Plus Complexe)

Niveau: Kernel

Note: Linux Mint utilise AppArmor par défaut, pas SELinux. Mais SELinux peut être installé.

Approche 4: Process Monitoring + Termination

import psutil import subprocess BLOCKED_APPS = { "firefox": None, "chrome": None, "steam": None, "vlc": None, # Peut contourner filtrage DNS } def monitor_processes(): for proc in psutil.process_iter(['pid', 'name']): if proc.info['name'] in BLOCKED_APPS: print(f"Killing blocked app: {proc.info['name']}") proc.kill() log_action(f"Blocked app attempted: {proc.info['name']}") while True: monitor_processes() time.sleep(5)
⚠️ Limitation: L'utilisateur peut renommer l'exécutable ou créer des liens symboliques. AppArmor est plus sécurisé car il identifie par inode, pas par nom.
Méthode Sécurité Contournement Performance
Permissions Très faible Facile (chmod si accès root) Excellent
AppArmor Très bonne Très difficile sans root Excellent
SELinux Excellente Pratiquement impossible Bon
Process Monitor Faible Renommer, symlinks Moyen (CPU)

5️⃣ Prérequis de Sécurité

Contrôle des Accès Root

Critique: root access

# L'application doit tourner en root pour: # - Modifier /etc/hosts ou dnsmasq # - Contrôler systemd sessions # - Utiliser iptables/firewall # - Charger modules AppArmor # Solution: sudo sans mot de passe pour actions spécifiques # /etc/sudoers.d/parental-control %parental-admin ALL=(ALL) NOPASSWD: /usr/local/bin/apply-parental-rules.sh %parental-admin ALL=(ALL) NOPASSWD: /usr/sbin/iptables

Protection de la Configuration

# Rendre la config read-only pour l'utilisateur enfant sudo chmod 600 /etc/parental-control/config.json sudo chown root:root /etc/parental-control/config.json # Empêcher modification du daemon chmod 555 /usr/local/bin/parental-daemon.py

Logging et Monitoring

# Stocker les logs en base de données (pas en fichier modifiable) # SQLite3 avec permissions restrictives /var/lib/parental-control/logs.db # 400 permissions
⚠️ Escalade de Privilèges: Un utilisateur avec accès administrateur local peut contourner n'importe quelle mesure logicielle. La solution doit viser les utilisateurs SANS droits root.

✅ Recommandations Finales

Pour une Solution Robuste :

  1. Combiner DNS + AppArmor + Monitoring systèmes (défense en profondeur)
  2. Stocker config en root-only pour empêcher modifications
  3. Implémenter 2FA/password fort pour compte parent
  4. Logger toutes tentatives de contournement en base de données chiffrée
  5. Contrôle BIOS/UEFI au niveau matériel pour éviter live USB
  6. Updater régulièrement les listes de sites (service cloud minimal)
  7. Audit de sécurité régulier pour identifier nouvelles failles

Limitation Intrinsèque :

Aucune solution logicielle n'est 100% sécurisée. Un utilisateur déterminé avec accès physique et temps peut toujours contourner. Les meilleures pratiques consistent à :

  • Rendre le contournement difficile et chronophage
  • Enregistrer les tentatives pour une conversation parent-enfant
  • Combiner avec supervision humaine (dialogue, confiance)
